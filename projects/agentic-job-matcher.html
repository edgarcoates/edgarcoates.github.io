Agentic Job Matcher

A multi-agent system that finds real graduate roles and ranks the ones a candidate both wants and can get. I built it so that every decision in the workflow can be explained, tested and priced.

The problem

I first ran my graduate search by talking to an AI assistant. It worked, but I couldn't repeat it and I couldn't audit it.

Each session started from scratch, judged roles a little differently, and left no record of why one posting was kept and another dropped. So I turned the process into an explicit graph: a leader agent and three sub-agents for research, role verification and alignment, with a feedback loop, typed hand-offs between agents, and an evaluation suite.

The design

A leader agent, three sub-agents and a loop with an explicit stop condition.

Engineering choices

A graph of narrow agents

Each agent has one narrow job, one output schema and its own model, so each can be tested, priced and debugged alone. Routing is ordinary Python over typed state.

Guardrails can veto but never force

Three gates (verified, wanted, attainable) are computed in code. The leader can reject a role that passes every gate. It cannot accept one that fails.

Cheap checks before expensive ones

Code rejects ineligible roles before any model sees them. Research returns a shortlist per round, and each fetched page is capped in size.

Parallel search, one lane each

A single generic search found zero to three roles a run. A focused search per lane finds more, and running them in parallel keeps the wall-clock time of one.

Preferences stored as numbers

Rubric weights, tier thresholds, bonuses and penalties live in config and are applied in code. The model judges each item with evidence; code does the arithmetic and the report shows every adjustment.

Every decision and cost is traced

Each run writes a report with the reasons for every decision, and a line-by-line trace of every model call with tokens, searches, cost and latency.

Runs can resume

State is checkpointed after every step. If a run stops, it continues from the last completed step, so paid-for work is never repeated.

Evals check which agent caught it

Seven designed postings each test one branch. The eval checks that each is caught by the agent built to catch it, and that the right posting wins. 42 offline tests cover rules, scoring and routing at no cost.

What real runs taught

Four of the failures that changed the design.

A rule that matters belongs in code, not just in the prompt.

What happened: the first live run proposed the same posting three times. The prompt told the research agent not to repeat roles, but the employer was worded differently each time, so nothing stopped it.

The fix: deduplication in code, on a normalised title and link, with a unit test.

Put every agent on the same clock.

What happened: the eval pinned "today" to a fixed date and the code checks used it. The leader's prompt never stated the date, so it used the real one, decided verification had the wrong date, and rejected a role that had passed every gate.

The fix: one shared date, stated in every agent's prompt. The eval caught it because it asserts the final pick, not just the gates.

Calibrate thresholds on real data, not the test set.

What happened: across three live runs, nine real roles were scored and none cleared the 22-out-of-30 bar, while the practice postings cleared it easily. Real postings rarely describe decision rights or ownership, and the agent scores silence low.

The fix: a second "worth applying" tier at 19, recency as a ranking bonus instead of a hard cut, and a focused search per lane.

Make tool failures visible before scaling up.

What happened: a large run across eleven lanes found nothing. It looked like an empty market. The per-lane summaries showed the search tool itself was erroring and timing out.

The fix: a simpler search tool, at most three lanes at a time, tool error codes on the console, and a one-lane test run before any big one.

Results

The latest live run: four lanes searched in parallel, one search round.

Real roles found20
Reviewed16
Shortlisted for application6

Of the 16 reviewed, 8 were rejected in code (experience, location, graduation year or role type) at no model cost. The whole run cost about $3.40, including web-search fees.

On the practice set, all seven designed postings were caught by the agent built to catch them, and the designed match was picked as a strong match. Across development, the evaluation suite and CI caught and fixed seven failure modes.

Scores still vary a little between runs: the same posting scored between 22 and 25 out of 30. Two independent gates keep the final decision stable, and a labelled set of real postings to measure agreement is the next thing I would build.
